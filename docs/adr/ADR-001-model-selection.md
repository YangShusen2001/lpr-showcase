# ADR-001：采用 HyperLPR3 预训练模型，而非自行训练

- **状态**：已接受
- **日期**：2026-09-17
- **决策人**：树森（需求/验收）· 架构师（方案/实现）

---

## 1. 背景与约束

本项目目标是产出一个**可在面试中现场演示、且结论可复现**的端到端车牌识别系统。

硬约束：

| 约束 | 具体限制 | 影响 |
|---|---|---|
| 硬件 | 15.4 GB 内存、**无独立显卡**、83 GB 可用磁盘 | 无法承担检测+识别两阶段的训练/微调 |
| 数据 | 无标注车牌数据集；中国车牌涉及合规敏感 | 自建大规模标注集不现实 |
| 时间 | 面试准备期 | 训练收敛周期不可控 |
| 交付 | 需要一个能在浏览器里跑的现场 Demo | 模型必须轻量、可导出为通用格式 |

用户明确指示：**「我这个电脑没有GPU会非常难受，所以我想的是直接去找，然后下载回来弄数据」** —— 即采用「取用成熟预训练模型」路线，而非「自行训练」。

---

## 2. 候选方案对比

| 方案 | 说明 | 评估 |
|---|---|---|
| **A. HyperLPR3**（szad670401/HyperLPR） | 中文车牌专用，三阶段 ONNX 已发布（检测/识别/分类），Apache-2.0 | ✅ 采用 |
| B. YOLOv9-t 车牌端到端模型 | 单模型直接出框，7.4~7.5 MB，许可证待确认 | ❌ 见下 |
| C. 自训练 CRNN + CTC | 需数万张标注样本 | ❌ 与硬件约束冲突 |
| D. PaddleOCR 车牌微调版 | 依赖 PaddlePaddle 生态，端侧导出链路长 | ❌ 增加不必要的工具链耦合 |

### 为什么否掉 B（YOLOv9-t）

B 在纸面上更简洁（一个模型出框），但实测直接否定了它：

- 256×256 输入：3 张测试图各检出 1 个框，置信度 0.90 / 0.91 / 0.95 —— 可用；
- 384×384 输入：仅 1 张检出（0.896），另两张置信度掉到 0.105 / 0.149 —— **低于 0.25 阈值**；
- 640×640 输入：**全部 0 检出**（最高 0.174）。

同一个模型在输入尺寸增大时检出能力反而崩塌，说明它的训练/导出配置与本批图像不匹配。一个需要反复试探输入尺寸才能出结果的检测器，不适合作为面试现场演示的基石。

### 为什么选择 A（HyperLPR3）

1. **模型是现成的 ONNX**，无需转换工具链，浏览器端可直接加载；
2. **体积可接受**：检测 2.23 MB + 识别 9.78 MB + 分类 1.53 MB = **14.2 MB**，Web 场景下无需切分；
3. **算法链路完整且可解释**：检测 → 透视矫正 → CRNN-CTC 识别 → 颜色分类，每一级的输入输出都能单独打印、单独验证 —— 这正是「能在面试里讲清楚」所需要的结构；
4. **许可证明确**：Apache-2.0，可公开演示；
5. **上游实现可读**：Python/C++ 源码在手，为「跨语言移植 + 数值保真」这条技术主线提供了参照基准。

---

## 3. 决策

**采用 HyperLPR3 三阶段预训练 ONNX 模型（方案 A），不自研训练。**

同时确定一条派生原则：

> **模型选型必须让「可验证性」优先于「先进性」。**
> 宁可选择一个已有公开参照实现的老模型，也不要选择一个更强但无法证明移植正确性的新模型 ——
> 因为本项目的技术价值在于「跨语言移植的数值保真」与「端侧性能表征」，而非「模型精度 SOTA」。

---

## 4. 后果

### 正面

- 项目可在数天内进入「端到端跑通」状态，把时间预算投入真正的差异化环节：移植保真度验证、端侧评测、论文写作。
- 每一个中间张量都有 Python 参照值可比对，这直接催生了 ADR-002 的验证方法学。
- 承认「模型是第三方预训练权重」在面试中是加分项而非减分项 —— 它把讨论从「你训练了什么」转向「你如何证明你的工程实现是对的」。

### 负面与缓解

| 风险 | 缓解 |
|---|---|
| 面试官追问「模型不是你训练的」 | 简历与展示页均明确标注模型来源与许可证，把重点放在移植、验证、端侧部署三件事上 |
| 识别精度受限于上游模型 | 不以「精度」作为项目指标；以「与 Python 参考实现的一致性」作为指标（可量化、可复现） |
| 上游模型对双层牌/新能源牌覆盖有限 | 已实测覆盖：蓝牌、黄牌、绿牌（8 位新能源）、双层牌切分逻辑均已实现 |
