# ADR-003：麒麟 8020 端侧部署路径与运行时缺陷

- **状态**：已接受（方法学已验证；车牌模型的端侧转换**已由 ADR-004 完成**）
- **日期**：2026-09-17
- **前置**：ADR-001
- **后续**：**ADR-004**（完成本节 §7 的全部待办，并替换 §6 的边界声明）

---

## 1. 问题

需求是「把模型部署到华为麒麟 SoC（如 8020）上」。约束：**无 GPU、无 Docker、不可用公网在线服务**。

需要回答两个问题：

1. 用什么工具链把 ONNX 送上麒麟 NPU？
2. 这条路径上有什么**没人写进文档的坑**？

---

## 2. 目标设备与工具链

| 项 | 值 |
|---|---|
| 设备 | HUAWEI nova 14 Pro（MIA-AL00） |
| SoC | 麒麟 8020 |
| 系统 | HarmonyOS 6 / OpenHarmony-6.1.1.120，SDK API 24 |
| 推理框架 | MindSpore Lite Kit 2.6.0 NDK（`OH_AI_*` C API） |
| 后端链路 | NNRT → NPU |
| NNRT 设备名 | `NPU_ohos.boot.hardware.kirin8020_v2_0` |
| 转换工具 | `converter_lite.exe`（PC 端，`mindspore-lite-2.6.0-win-x64`） |

宿主形态：自研 ArkTS + NAPI C++ 应用，通过 `OH_AI_ModelBuildFromFile` 加载 `.ms` 模型。

---

## 3. 决策

**采用 MindSpore Lite → NNRT → NPU 路径，并在宿主侧做三件必须做的事：**

### 3.1 会话必须常驻，不能反复析构

NNRT delegate 的析构路径存在 cppcrash。若每次推理都创建/销毁会话，
应用会在若干轮之后崩溃。

**决策**：模型会话在应用生命周期内常驻，只复用、不重建。

### 3.2 设备名不能靠猜，必须从系统读

NNRT 设备名并非稳定的通用常量：

- 早期文档与部分设备上为 `HIAI_F`；
- 本机（麒麟 8020）实际为 `NPU_ohos.boot.hardware.kirin8020_v2_0`。

**决策**：设备名从设备侧读取后传入，不硬编码单一字符串。

### 3.3 动态 batch 维度会导致构图失败

带动态 batch 维度的模型在 `OH_AI_ModelBuildFromFile` 阶段直接失败。

**决策**：转换时固定 batch = 1。

### 3.4 无法依赖 hitrace 观测 NPU 活动

系统未开放 NPU 相关的 hitrace tag，因此不能通过 trace 直接确认算子是否真的落在 NPU 上。

**决策**：改用 **CPU-diff 方法** —— 同一模型分别指定 CPU 与 NPU 后端各跑一遍，
用延迟差与输出一致性共同判定委托是否生效。该方法贯穿全部评测。

---

## 4. 已定位的运行时缺陷

### 4.1 FP16 输出缓冲区被声明为 FP32（数值爆炸）

**现象**：经 `converter_lite --fp16=on` 转换的模型，部分输出张量声明
`OH_AI_DATATYPE_NUMBERTYPE_FLOAT32`（枚举值 43），但缓冲区实际内容是 **FP16 位流**。

**后果**：应用按声明的 FP32 读取，得到 1e8 ~ 1e21 量级的垃圾值。

**证据**：`yolov8n` 的输出 L2 范数

| 后端 | 输出 L2 |
|---|---|
| NPU | 3.93 × 10²¹ |
| CPU | 50569.64 |
| 相对误差 | 7.78 × 10¹⁸ % |

把同一段内存按 FP16 重新解释，数值完全正确。

**缓解**：在计算图尾部显式插入 Cast 节点（产物即 `yolov8n_fix`），
相对误差收敛到 **0.015%**。

**另一条同样不可救的路径**：官方模型库中的 `mobilenetv2.ms` / `ghostnet_int8.ms`
（Mate30 时期产物）在**所有设备、包括 CPU 后端**上 `OH_AI_ModelBuildFromFile` 均返回 `ret = -1`，
且无错误详情；PC 端用 `converter_lite 2.6` 重新序列化同样失败 —— 1.x 时代工件已无法被现行工具链读取。

### 4.2 结果解读：为什么这属于「表征」而非「调参」

这两个缺陷都属于**运行时契约不成立**（声明的 dtype 与实际不符、版本兼容性断裂），
而不是模型精度问题。它们构成端侧部署的真实风险面，也是本评测相对「跑个 benchmark」的差异化价值。

## 5. 实测结果（麒麟 8020）

协议：warm-up 10 次 + 正式 100 次取 P50；采集时电量 100%、电池温度 36.0 °C、thermal level 2。

| 模型 | NPU P50 (ms) | CPU P50 (ms) | 加速比 | 输出一致性 |
|---|---|---|---|---|
| resnet50 | 6.02 | 78.90 | **13.11×** | 0.242% PASS |
| resnet18 | 3.27 | 34.00 | **10.39×** | 0.000% PASS |
| yolov8n | 15.60 | 71.07 | **4.56×** | 见 §4.1 FAIL |
| mobilenetv2 | 2.74 | 10.22 | **3.72×** | 0.067% PASS |
| mobilenet_v3_small | 3.37 | 3.44 | **1.02×** | 0.289% PASS |
| mobilenetv2_int8 | 5.08 | 4.97 | **0.98×** | 0.000% PASS |

### 关键结论

**加速比随模型规模单调上升（13.11× → 0.98×）。**

小模型在 NPU 上拿不到收益，全 INT8 量化的 mobilenetv2 甚至比 CPU 慢 2%。
原因指向固定的委托开销（图切分、委托下发、算子回退）在小图上无法被摊薄。

**端侧选型判据**：先评估算子覆盖与图规模，再决定是否上 NPU；不要默认「上了 NPU 就一定快」。

### 数据质量声明

当前为 1 轮采集（协议要求 ≥ 5 轮），CI 仅供参考；
`ghostnet_int8_official` 与 `mnv2_official` 存在失败轮次，数据缺失；
热态标注：thermal level 从 2 升到 3 时 NPU 延迟上升 15~20%，CPU 上升 < 2% —— 因此加速比必须标注热状态。

## 6. 边界（诚实声明）

> **本节数据来自同机型的独立 NPU 评测程序（`ShusenPaper`），评测对象是通用骨干网络
> （resnet / mobilenet / yolov8n），不是本项目的三个车牌模型。**

**尚未完成**：把 `y5fu_320x_sim.onnx` / `rpv3_mdict_160_r3.onnx` / `litemodel_cls_96x_r1.onnx`
转换为 `.ms` 并部署到 NPU 上端到端跑通。

**为何不阻塞**：本项目已验证的是**方法学**（转换链路、宿主侧约束、缺陷定位手法、评测协议），
而不是某个特定模型的端侧数字。把方法学与模型结果混为一谈才是真正的风险。

**面试口径**：表述为「已完成端侧部署与评测方法学，车牌模型的端侧转换待完成」。
