## 1. 标准版（6 条，约 390 字）

**基于 HyperLPR3 的端到端车牌识别与跨语言移植保真验证｜个人项目｜独立完成**

- 基于 HyperLPR3 三阶段预训练 ONNX 模型（检测 2.23 MB / CRNN-CTC 识别 9.78 MB / 颜色分类 1.53 MB），
  实现「检测 → 透视矫正 → 序列识别 → 颜色分类」完整流水线，支持蓝牌、黄牌、绿牌（8 位新能源）与双层牌切分识别。

- 将 C++/Python 参考实现逐行移植为无依赖的 ES Module，使用 onnxruntime-web（WASM + SIMD，线程数自适应）
  在浏览器内完成全部推理，**0 个外部网络请求**，任意静态服务器均可部署；1140×456 场景端到端 **85 ms**
  （麒麟 8020 手机端，6 线程 WASM；单线程 126 ms，提速 1.5×）。

- **数值保真（核心贡献）**：逆向 OpenCV `cv2.resize` 的定点实现（11 位系数、两趟分离、末尾单次合并舍入
  `>> 22`），使 JS 与 Python 参考在整数缩放比下达到**逐通道完全一致**；定位并修复关键点未先截断导致的
  1 px 裁剪偏移缺陷（该缺陷会让识别结果从 `MU4158` 变为 `H468`）；最终 **8/8 测试样本**识别结果与 Python 参考一致。

- 对非整数缩放比下的残余误差给出量化边界：最坏样本 307200 个通道中 11753 个相差 ±1 个量化级、
  符号单一，且不影响任何识别输出 —— 经 135 个尺寸扫描定位为 OpenCV 垂直趟定点累加产物（垂直比例为 1 时
  不一致像素仅 0.11%，否则 29.1%），明确声明不追求位级一致而非掩盖。

- **端侧部署与评测（麒麟 8020 / HarmonyOS）**：MindSpore Lite 2.6.0 → NNRT，在 nova 14 Pro 上完成
  「3 车牌模型 × 4 后端」全矩阵评测（另含 4 个图手术变体），以**实际落点** `LANDED=` 判定而非请求后端：
  识别模型落 NPU **2.2–3.0×**（2.97–4.17 ms vs 8.97–9.02 ms）；检测模型因 YOLOv5 anchor-grid decode
  的 rank-5 常量**四条补救路径全部回落 CPU**，判定为模型侧边界而非配置问题。另定位 FP16 输出缓冲区
  被声明为 FP32 的数值爆炸缺陷，图尾插入 Cast 后相对误差从 7.78e18% 收敛到 0.015%；
  通用骨干扫描中 ResNet-50 达 6.02 ms（NPU）/ 78.90 ms（CPU）。

- **精度基准与自我证伪**：在第三方真实人工标注集（1000 张裁剪图，文件名即真值）上测得识别器
  **906/1000 = 90.6%**，与候选替换模型 LPRNet（88.8%，McNemar **p=0.1788** 不显著）做配对检验后
  **判定不换**，并给出优势项量化：长度错误率 1.0% vs 7.0%。同一批测量还**推翻了本项目一直当作
  验收红线的单图"真值"** —— 那个串其实只是被测模型自己的输出（循环论证），修正后正确真值是
  8 字符的 `苏ED51712`；配套证伪实验（n=200）证明水平拉伸不会凭空多出字符、压缩 17% 会吃字符。

## 4. 面试口径与边界（务必先读）

| 面试官可能问 | 应当如何回答 |
|---|---|
| 「模型是你训练的吗？」 | 不是。用的是 HyperLPR3 的公开预训练权重（Apache-2.0）。**我的贡献是跨语言移植的数值保真验证 + 端侧部署评测**，不是模型训练。 |
| 「识别准确率多少？」 | **90.6%**（906/1000），数据是第三方公开集里的真实裁剪图、**文件名即人工真值**，不是我自己合成的。要同时给出边界：该集 1000 张**全是 7 字符普通牌，新能源 8 位牌 0 张**，所以不外推"路况准确率"；对照候选模型 LPRNet 88.8%，McNemar p=0.1788 不显著。**早期版本这里写的是"我不报准确率"** —— 那时确实没有标注基准，报了就是编；后来补上了，就把旧口径一起改掉，而不是继续引用它。 |
| 「车牌识别在麒麟 NPU 上跑通了吗？」 | **跑通了 2/3**。三个车牌 ONNX 已全部转成 `.ms` 并上机跑矩阵：识别模型（CRNN-CTC）NPU **2.97–4.17 ms** 对 CPU 8.97–9.02 ms（**2.2–3.0×**），分类模型也已落 NPU；**检测模型（YOLOv5 系）上不去** —— 图内 12 个 rank-5 常量触发 HiAI `CreateConstOp failed`，四条图手术路线已全部证伪，出路是导出裸 head。同机型上另有一套通用骨干网评测（ResNet-50 13.11×），那是方法学验证阶段的产物。⚠️ 限定条件要说清：「检测上 NPU 会翻字符」**只在 NPU-fp16 下测过**（`addNnrt()` 恒传 `fp16=true`，NNRT-fp32 从未试），所以严格表述是"检测不能在 NPU-fp16 上用"；被追问"怎么确定不是 fp16 的锅"时，答"我还没排除，这是当前结论的已知缺口"（ADR-015），不要硬撑。 |
| 「为什么加速比差距这么大？」 | 加速比随模型规模单调上升，13.11× 到 0.98×。小图上固定的委托开销摊不掉，全 INT8 量化的 MobileNetV2 反而比 CPU 慢 2%。所以端侧选型要先看算子覆盖与图规模。 |
| 「为什么不用更大的模型？」 | 项目目标是「可验证性」而非「精度 SOTA」。选一个已有公开参照实现的老模型，才能证明我的移植是对的 —— 这是刻意的取舍，写在 ADR-001 里。 |

### 绝对不要说的话

- ❌「识别准确率 99%」→ 实测是 **90.6%（906/1000，第三方真实标注集）**。不要四舍五入成"高准确率"，
  也不要把它说成路况指标（该集无 8 位新能源牌）
- ❌ 把 **8/8 一致**说成"识别全对"→ 它只证明 JS 移植与 Python 参考**输出相同**，与真值无关；
  该命题的反例正是本项目自己抓到的：参照串 `苏ED5172` 本身是错的（真值 8 字符）—— 见 ADR-015
- ❌「三个车牌模型都跑在 NPU 上」→ 只有识别与分类跑通，**检测模型回落 CPU**（根因已定位，见 ADR-004）
- ❌「我训练了这个模型」→ 不实
- ❌「移植后与 Python 完全一致」→ 准确说法是「整数缩放比下逐通道一致；非整数缩放比下残余 ≤1 量化级，不影响输出」
