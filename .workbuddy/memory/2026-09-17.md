## 追加 · Demo 在编辑器预览里打不开（根因：扩展名白名单）

### 症状与误判路径

用户报错：`Failed to fetch dynamically imported module:
http://127.0.0.1:10504/static-html/ca16d81693108742/assets/ort/ort.min.mjs`

第一反应是「文件太大 / 路径不对」，都不对。HEAD 探测给出决定性反证：

```
assets/ort/ort-wasm-simd-threaded.wasm     200  application/wasm     （13.3 MB 放行！）
assets/ort/ort.min.mjs                     403  ← 白名单外
assets/models/y5fu_320x_sim.onnx           403  ← 白名单外
```

**被拦的是扩展名，不是体积。** 编辑器预览服务按扩展名白名单放行
（`html/css/js/json/wasm/jpg/png/webp`），白名单外一律 **403 Forbidden**（不是 404）。

### 解法：改名（浏览器只认字节，不认扩展名）

| 原 | 现 |
|---|---|
| `assets/ort/ort.min.mjs` | `assets/ort/ort.min.js` |
| `assets/ort/ort-wasm-simd-threaded.mjs` | `assets/ort/ort-wasm-simd-threaded.js` |
| `assets/models/y5fu_320x_sim.onnx` | `assets/models/y5fu_320x_sim.onnx.json` |
| `assets/models/rpv3_mdict_160_r3.onnx` | `assets/models/rpv3_mdict_160_r3.onnx.json` |
| `assets/models/litemodel_cls_96x_r1.onnx` | `assets/models/litemodel_cls_96x_r1.onnx.json` |

保留 `.onnx` 字样是为了自解释（「ONNX 文件 + 一个白名单后缀」）。
未用于运行时的模型（`y5fu_640x_sim`、三个 YOLOv9）**不动**。

### 配套代码约束（三处，缺一即复发）

1. `demo.js` 的 `import('../ort/ort.min.js')`
2. `ort.env.wasm.wasmPaths` 必须用**对象形式**显式给出改名后的 worker：
   `{ mjs: '.../ort-wasm-simd-threaded.js', wasm: '.../ort-wasm-simd-threaded.wasm' }`。
   写成目录字符串 `'../ort/'` 会让 ORT 自己拼出 `.mjs` → 又踩回 403。
3. `InferenceSession.create` 的 option 里显式 `format: 'onnx'` ——
   否则 `.onnx.json` 会让 ORT 的格式猜测器以为这是 ORT 自家 JSON 格式。

### 连带修复：Python 参考实现差点被改名搞死

`tools/hlpr_reference.py` 的 `sess()` 读 `assets/models/<name>.onnx`，
改名后它是**唯一一份**模型，会直接 `FileNotFoundError` —— 而它是保真度验证的 ground truth。
→ 新增 `model_path()`：先找 `.onnx`，找不到再找 `.onnx.json`。
**刻意不复制第二份 14 MB 模型**：两份必然漂移，而「Python 与浏览器跑同一份字节」是本项目核心主张。
实测 `python tools/hlpr_reference.py` → EXIT=0，`MU4158` / `苏ED5172` 与 ADR-002 完全一致。

### 复测

| 检查 | 结果 |
|---|---|
| 编辑器预览服务 HEAD 全部改名资源 | 200（`.wasm` 13.3 MB 也是 200） |
| `demo.html?auto=1` | `done=true`，`藏DT5022`，128.6 ms，`errors=[]`，`consoleErrors=[]`，1.79 屏 |
| `index.html?auto=1` | `done=true`，`藏DT5022`，135.7 ms，`errors=[]`，`consoleErrors=[]` |

   1-D 扫描（垂直比例恒为 1）平坦 0.01–0.23%；2-D 扫描整体 19.44%，
   按小数坐标分箱仍平坦（18.3–25.0%），但**按垂直比例切分立刻分开**：
   垂直比例 = 1 时 **0.113%**，≠ 1 时 **29.108%**。
3. **偏差方向反了**：OpenCV `cv2.resize` 系统性**低于**精确双线性（负偏差）；
   已交付的移植实现更接近精确值（因为它把水平中间量按全精度携带）。
   所以「移植 vs OpenCV」的偏差是**正**的 —— 与旧文陈述方向相反。

### 本机 LaTeX 环境陷阱（务必记住）

1. **tectonic v0.15 的裸形式是 `tectonic <file>`**；`compile` 子命令只在 `-X` 后面存在。
   写成 `tectonic compile main.tex` 会把 `compile` 当成输入文件名 → 报
   "Found argument ... which wasn't expected"。
2. **PowerShell 直接调 tectonic 会被安全扫描拦**（"Encoded commands hide the actual code"），
   而且**任何含中文的 PowerShell 命令都被拦**。→ 一律走 Python `subprocess`；
   脚本内部用 `Path(__file__).resolve().parent.parent` 定位，**不把中文路径写到命令行**。
3. **IEEEtran 正文是纯拉丁字体，`\texttt{藏DT5022}` 的汉字会被静默丢弃**
   （`Missing character: no 藏 in font lmroman8`），表格里那格变空白。
   → 加 `\usepackage{xeCJK}` + Fandol（TeX 自带，无需系统字体）：
   `\setCJKmainfont{FandolSong-Regular.otf}` / `\setCJKmonofont{FandolFang-Regular.otf}`。
   xeCJK 会把 CJK 码点路由到 CJK 字体，**即使在 `\texttt` 内部**。
4. **长标识符 + xeCJK = 整行溢出 5 cm**。根因：ctex 默认 `CJKspace=true`，
   源文件里「汉字↔英文」之间的空格被吃掉，于是 `OH_AI_DATATYPE_NUMBERTYPE_FLOAT32`
   与前面的中文焊成**一个不可断的整体**，TeX 只能让整行冲出边界（实测 146.9pt）。
   → 用 `\path{}`（url 宏包）让标识符可在 `_ . / =` 后断行，并补 `\UrlBreaks` 缺的 `-` 和 `*`：
   ```latex
   \makeatletter \g@addto@macro\UrlBreaks{\do\-\do\*} \makeatother
   \Urlmuskip=0mu plus 1mu
   \setlength{\emergencystretch}{2em}
   ```
5. **`verbatim` 在 IEEEtran 单栏里一行最多 48 字符**（实测 5.25pt/字符，栏宽 252pt）。
   超出就静默冲出栏外。→ 代码行必须主动折到 ≤45 字符。
6. **表格列宽要按「不可断的最长片段」算**，不是按整体宽度。
   例：`\textbf{Letterbox}` 加粗 8pt 需 1.59cm，给 1.30cm 就溢出 5.06pt；
   `1920$\times$1080,` 需 1.46cm。→ 用 `\setlength{\tabcolsep}{4pt}` + 逐列量宽。
7. **表格里 `String` 列必须能装下整块车牌**（如 `粤ZP560港`：2 个 CJK + 5 拉丁）。
   列宽不足时 xeCJK 会在汉字与车牌主体之间断开，出现「省简称独占一行」的怪排版。
   验证方法：`pdf_render_check.py --find ZP560`，抽取行应是 `粤ZP560 港`（同一行）。

### 2. 实测矩阵（`matrix_and_web.txt`，两轮复现）

| 模型 | `nnrt` | `gpu`/`kirin` | p50 |
|---|---|---|---|
| `rpv3_mdict_160_r3` 识别 | **NPU** | 回落 CPU | **2.97–4.17 ms**（CPU 8.97–9.02） |
| `litemodel_cls_96x_r1_fp32` 分类 | **NPU** | 回落 CPU | 0.96–1.09 ms |

### 3. 三个根因（全部是**边界**，不是配置）

1. **检测模型上不了 NPU**：图内 **12 个 rank-5 常量**（`[1,3,40,40,15]` 等，
   YOLOv5 anchor-grid decode 烘进图）→ `Tensorptr format not support` +
   `get weight shape is empty` + `CreateConstOp failed`。
   四条图手术路线（`s1` / `s1r4` / `flat` / `surgery`）**全部证伪**，
   且手术本身数值逐位等价（`max_abs_diff=0`）—— 是「改了也进不去」，不是「改坏了」。
   → 唯一出路：**模型侧改造**（导出无 anchor-grid decode 的裸 head）。
   检索印证：华为 NPU 上部署 YOLO，业界通行做法正是改结构（MaxPool→AvgPool、Focus 拆解、SiLU 替换）。
2. **原生 GPU 不存在**：`inner_context.cc:207 IsValid# GPU is not supported.`（编译期判否）。
   MindSpore Lite 的 GPU 后端基于 OpenCL，麒麟 8020 未暴露设备。
3. **ArkWeb 里 ORT 的 GPU 路径被上游删除**：ORT **v1.29.0**（正是本项目锁定版本）
   release notes 宣布 deprecation of WebGL & JSEP，`onnxruntime-web/webgl` 子路径移除，
   唯一 GPU 路径是 WebGPU EP（#29716、#31683）；而实测 `requestAdapter()` = **NULL**。
   → 本项目页面选 WASM 不是妥协，是**该平台唯一可用的 ORT 配置**。

### 4. ⚠ 自己猜翻车的实例（探针字节码）

初版 Web 探针用手写 WASM 检测字节码，报出 `wasm.bulkMemory=false`、`wasm.truncSat=false`
—— **两个都是假结论**：

- `memory.copy` 后面只写了一个 memidx 字节（`252,10,0,11`），官方是两个（`252,10,0,0,11`），段长也算成 13 而非 14；
- `trunc_sat` 声明 `result i32` 却没消费栈顶（缺 `26` = drop）→ 模块非法。

**更正**：字节码逐字节取自 `wasm-feature-detect` 官方实现，**先在本机 Node 22 校验
`validate=true`** 才上机（`wasm_bytes_verified.json`）。实测修正后：
SIMD / bulkMemory / truncSat / signExtensions / multiValue / referenceTypes / bigInt
**全部 true**。

> 教训：**一个字节的偏差 = 一个假结论**。字节级构造必须引用权威实现。

## 12. 检测模型上 NPU：裁掉 decode（17:30–17:45）

用户问「①能改算子吗 ②按照你说的来」。① 的答案是**能，而且已经做到一半**。

### 12.1 做了什么

**不修改 decode，而是把 decode 整段裁掉**（ADR-004 §4.1 的 4 种手术都是在保留 decode
的前提下改 rank，全败；换成"裁"就成了）：

`tools/export_bare_head.py`：从三个 head conv 输出（`948`/`1061`/`1174`）**反向可达**
→ 只保留产生它们所需的节点 → **416 → 313 节点，rank-5 常量 12 → 0**。

### 12.2 对照实验（决定性）

| 版本 | 切点 | 输出 | 落点 | p50 |
|---|---|---|---|---|
| **A** | head conv 输出 `948/1061/1174` | `[1,45,H,W]` rank-4 | **NPU** | **4.95 ms** |
| B | sigmoid 之后 `980/1093/1206` | `[1,3,H,W,15]` rank-5 | CPU | 7.52 ms |

**A 版成功** → ADR-004 §4.1 的判定正确。CPU 9.07 → NPU 4.95 ms（1.83×）。

### 12.3 真正的算子缺口：Reshape / Permute（修正了此前的表述）

B 版回落的原因在原始日志里：

```
W AI_NPUCL: op [Reshape_501] type [Reshape] is not supported in npucl store [fe_lib]
W AI_NPUCL: op [Reshape_597] type [Reshape] is not supported
```

`Reshape_501/597` = decode 的第一个 Reshape。**它不在 NPU 算子库 → 从它开始的子图整体回落。**

> **Reshape / Transpose(Permute) 是麒麟 8020 NPU 的算子缺口。**
> 这与 rpv3 的 `svtr_block.{0,1}/mixer` 报的是**同一类算子、同一根因**。

**所以「能改算子吗」的准确答案**：
- 检测（y5fu）：裁掉 decode → **已上 NPU**
- 识别（rpv3）：要消除 `mixer` 的 Reshape/Permute（不是 rank 问题），收益上限约 9→3ms
- **不是 rank 问题，是 Reshape/Permute 支持问题**

### 12.4 decode 数学（已解开，供 C++ 实现）

```
cx = (sigmoid(t0)*2 - 0.5 + grid_idx_x) * stride
w  = (sigmoid(t2)*2)^2 * anchor_w
obj = sigmoid(t4)
kpt_i_x = t[5+2i] * anchor_w + grid_px_x     ← kpt 通道【不做 sigmoid】！
cls = sigmoid(t13:15)
```

**两个反直觉点**（实测反推，别凭直觉写）：
1. **kpt 通道在 `982` 里是原始 logits**。实测 `982` 的 ch5 范围 `[-2.465, 1.396]`（超出
   sigmoid 的 [0,1]），而 ch0/1/2/4/13 与 `sigmoid(raw)` **逐位相等**。
   图里只对 `[0:5]` 和 `[13:15]` 调 Sigmoid。
2. **kpt 乘 anchor（不是 stride）**，加 grid **像素**值；cx/cy 加 grid **索引**再整体乘 stride。

anchors（9 对，可硬编码）：40×40→`(4,5)(8,10)(13,16)`；20×20→`(23,29)(43,55)(73,105)`；
10×10→`(146,217)(231,300)(335,433)`。grid 可 `x*stride` 程序生成。

## 13. 按官方支持清单选模型：NPU 的真实算子约束（17:45–18:00）

### 13.1 官方列表 vs 实测（关键落差）

华为官方「支持的算子」列表里，**`Reshape` / `Permute` / `Swish` / `GatherV2D` / `LSTM` /
`SSDDetectionOutput` / `NonMaxSuppressionV3D/V6` 全都在列**。

**但只看这张表会得出错误结论**——实测约束写在编译器内部检查里，文档上没有：

```
permute_check_support.cc      IsSupport(21):: realdimCnt > 4
reshape_check_support.cc      ReshapeCheckFunc(41):: check reshape dimInfo fail
permute_matmul_fusion_pass.cc IsMatch(91):: permute node:... only support order 0132
squeeze_graph_builder.cc      RecoverShape(33):: wrong input dims
```

**→ 选型判据（ADR-007 核心产出）**：
**① 所有张量 rank ≤ 4；② 所有 Transpose 的 perm 只能是 `[0,1,3,2]`（或可被融合消除）。**
「算子名在支持列表里」不等于「这个模型能上 NPU」。

### 13.2 LPRNet：静态指标全绿，仍被一个 perm 挡住

LPRNet（`rknn_model_zoo/examples/LPRNet`，纯卷积+CTC 无 RNN，1.7MB）静态指标**全合格**：
63 节点、rank≥5 常量 **0**、initializer 最大 rank-4、**无 Reshape**、算子全在官方列表、
输入 `[1,3,24,94]` / 输出 `[1,68,18]`。

**实测仍 `LANDED=CPU`**：**6 个 Transpose 全是 `perm=[0,3,2,1]`**，而 NPU 只认 `[0,1,3,2]`。
→ **静态指标全绿 ≠ 能上 NPU，perm 是独立的一道门。**

### 13.3 但 LPRNet 的 Transpose 全部可消除（方案已定）

三对固定模式：

| 位置 | 结构 | 等价改写 |
|---|---|---|
| `_2→_3→_4→_5` | `MaxPool k=3x3 s=1` → `T` → **`MaxPool k=1x1 s=1`** → `T` | **整体恒等 → 直接删** |
| `_14→_15→_16→_17` | `MaxPool k=3x3 s=[1,2]` → `T` → **`MaxPool k=1x1 s=[1,2]`** → `T` | 1×1 窗口+stride=纯抽样 → **沿 W 维 `Slice(step=2)`** |
| `_34→_35→_36→_37` | 同上，stride 4 | **沿 W 维 `Slice(step=4)`** |

**原理**：`Transpose[0,3,2,1]` **自逆**（作用两次回原状），中间 MaxPool 窗口是 **1×1**
（不聚合邻域，只按 stride 抽样）→ 整对 = 在转置布局上沿某维抽样 = 原布局上对该维 `Slice`。
**`Slice`/`StridedSlice` 都在官方支持列表里**。

## 14. LPRNet perm 改造：消除了 perm，但 NPU 仍不收（17:50–18:00）

### 14.1 改造成功，且数值零损失

`tools/fix_lprnet_perm.py`：**6 个 `Transpose[0,3,2,1]` 全部消除**，63 → 56 节点。

**验证**：`orig (1,68,18)` vs `fixed (1,68,18)`，**`maxAbsDiff = 0.00000000` → MATCH**。
→ 满足用户「性能不能有损失」的要求。

**等价改写（关键：由 runtime shape 反推，不是猜的）**：

```
79:(1,128,18,44) → 80:(1,44,18,128) → 81:(1,44,18,64) → 82:(1,64,18,44)
                                          ↑ 变化的永远是最后一维
```

**`[0,3,2,1]` 后布局是 `[N,W,H,C]`，而 ONNX MaxPool 只池化 dims 2,3** →
`strides=[1,S]` 作用在 **dim3 = 原通道轴**，不是我以为的 W 轴。
→ 等价于 **`Gather(axis=1, step=S)`**（`Gather` 在官方支持列表里）。
→ 第 1 对 `66:(1,64,20,90)` 与 `69:(1,64,20,90)` shape 相同 → **整体恒等，直接删**。

**两个中间踩的坑**：
- 一开始想用 5 输入 `Slice` → **该图 opset 太低不支持**，改用 `Gather`
- `Gather` 的 indices 先用了 INT64 → 改 INT32（虽然后来证明与本问题无关）
- 第 1 对"直接删"时**忘了重连下游引用** → `Node input '69' is not a graph input...`

### 14.2 但真机仍然 `LANDED=CPU`

静态扫描**两道门全过**：`rank>=5 consts: 0`、`Transpose perms: {}`、`Reshape: 0`
→ `GATE1 PASS | GATE2 PASS | LIKELY NPU-OK`。

**实测仍回落**，且**没有任何「算子 X not supported」**，只有：

```
8x AI_NPUCL: op_supported_format.cc GetOpSupportedFormat(403):: The type of Data not find.
4x MS_LITE:  [scheduler.cc:645] InitDelegateKernels# Inner delegate replace delegate kernels failed.
4x MS_LITE:  [model_impl.cc:206] Build# Init session failed
```

**排查**：原始 LPRNet 的 36 个常量**全是 FLOAT、无 INT** → 该报错**改造前就存在**，
与 dtype 无关。真正原因**未定位**（需要逐算子二分）。

### 14.3 结论（方法论修正）

> **rank ≤ 4 与 perm == [0,1,3,2] 是必要条件，但不充分。**
> 两道门都过了，仍可能被 `InitDelegateKernels` 拒绝。

**y5fu 裸 head 能过**（313 节点、无 Transpose/Reshape、算子少），
**LPRNet 不能**（有 ReduceMean/Pow/Div/AveragePool/Pad/Gather 等杂算子）。
→ **经验规律：NPU 接受的模型是「算子集合窄 + 无布局变换」的那一类**，
不是「只要满足 rank/perm 就行」。
